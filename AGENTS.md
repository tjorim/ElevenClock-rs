# AGENTS.md

This file provides guidance to coding agents (including Claude Code) when working with code in this repository.

ElevenClock-rs is a Rust rewrite of ElevenClock: a Windows 11 app that draws a custom
date/time overlay on top of the taskbar clock (never modifying or hiding the native
clock). `docs/contributing.md` is the authoritative contributor guide; `docs/README.md`
maps the design records and ADRs.

## Commands

Rust 2024 on current stable (no pinned toolchain). Run from the repository root; it is a
virtual workspace whose default member is `clock-app`, so use `-p` or `--workspace` for
anything else. Always pass `--locked`.

```sh
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test -p clock-core --locked                 # portable, any host
cargo test -p clock-windows --locked              # portable parts run on Linux too
cargo test -p clock-core --test state <name>      # single test: target + name filter
```

Windows-only code is gated on `cfg(windows)`. On Linux, type-check and lint it with
`--target x86_64-pc-windows-msvc` (needs the target installed); it cannot be executed:

```sh
cargo clippy -p clock-windows -p clock-app --all-targets --target x86_64-pc-windows-msvc -- -D warnings
```

`--workspace --all-targets` for the Windows target fails on Linux because Criterion's
`alloca` needs MSVC. Release builds (`cargo build -p clock-app --release --target
x86_64-pc-windows-msvc`) require a Windows host with the MSVC toolchain and SDK resource
compiler; `clock-app/build.rs` refuses a cross-compiled release. Real Win32/COM behaviour
is verified by the Windows CI jobs (`rust-ci.yml`, `runtime-lifecycle.yml`).

Special test targets: `discovery_worker` and `uia_lifetime` use a custom `main`
(`harness = false`); `clipboard_native` tests are `#[ignore]`d because they overwrite the
clipboard (`-- --ignored --test-threads=1`).

## Win32 bindings

There is no `windows` crate. Win32 APIs come from bindings generated by `windows-bindgen`
into `crates/clock-windows/src/bindings/generated.rs` (checked in; CI fails if stale):

- Add the name (`Windows.Win32.<Name>`, or `Windows.Win32.IFoo::{Method, ...}` for COM
  methods, listed on the interface that declares them) to `crates/clock-windows/bindings.txt`,
  then `cargo run -p clock-bindgen`.
- `crates/clock-windows/src/bindings.rs` hand-writes what the metadata lacks
  (UIAutomationCore.dll exports, UIA ids, `FOLDERID_LocalAppData`) and adds `CheckHandle`
  (`.ok()` / `.valid()` / `.is_invalid()` for raw handle returns).
- Constants are plain integers (mostly `i32`): cast with `as u32` at call sites, and
  `match message as i32` for window procedures. A constant missing from the bindings in a
  `match` arm silently becomes a catch-all binding.
- `windows-core`, `windows-numerics` and `windows-bindgen` must stay on the same version.

## Architecture

Crates (dependency direction app → windows → core, app → core):

- **`clock-core`**: platform-independent, no unsafe, no Windows crates. The format
  language (`format.rs`, spec in `FORMAT.md`), validated preferences, and the pure clock
  state machine: `reduce(state, event) -> (state, Vec<Effect>)` in `state.rs`. It reads
  no time and owns no resources; the runtime feeds it events (Tick, DiscoveryResult,
  ExplorerLost, SessionLocked, ...) and executes its effects. See
  `docs/design/state-and-scheduling.md`.
- **`clock-windows`**: owns all FFI. Most modules are split into portable logic (tested on
  any host) plus a `native.rs` (Windows-only). `runtime::Runtime` is generic over a
  `Platform` trait and tested on Linux with a scripted platform; `runtime::native` is the
  real message loop, host window, timers and overlay windows. Other areas: `taskbar`
  (discovery), `render` (DirectWrite/Direct2D), `settings` (Win32 dialog, rules in
  `settings_model`), `accessibility` (UIA provider), `startup` (HKCU Run value),
  `support`/`logging` (diagnostics), `instance` (single instance and process roles).
- **`clock-app`**: thin `#![forbid(unsafe_code)]` entry point and the linked resources
  (dialog, icon, DPI-v2 manifest). `instance::Role` decides whether the process is the
  app or the taskbar discovery helper.
- **`clock-bindgen`**: development-only generator for the Win32 bindings.

Cross-cutting rules (details in `docs/contributing.md` and the ADRs):

- Taskbar discovery (UI Automation probing) is blocking work done in a separate helper
  process: the same executable started with a private marker (ADR 0001, ADR 0002). It
  never runs in application callbacks. Responses carry a `ShellGeneration` (an Explorer
  identity); stale generations are discarded and Explorer restarts destroy old overlays.
- Native handles and COM pointers never cross worker channels; window/dialog callbacks
  store no borrowed state and never unwind across FFI.
- Monitor/taskbar IDs are process-local values, never raw handles or persisted IDs.
- Only `clock-app`'s release executable ships. Examples (`taskbar_probe`,
  `overlay_evidence`), tests and scripts are development artifacts.
- The diagnostics report must stay free of user names, paths and window titles
  (golden text and redaction cases in `support/tests.rs`).
- Startup touches only this app's own `ElevenClockRust` Run value and `StartupApproved`
  flag, and only on explicit user action.

## Docs and dependencies

The website is an Astro build (`site/`, Node 24.14.0, npm 10.9.8) that renders the Markdown in
`docs/`, `README.md`, `CODE_OF_CONDUCT.md` and `FORMAT.md` as the single source. Check
website changes with `npm ci && npm test && npm run build && npm run check:site`; new
pages go into `site/lib/nav.mjs` (details in `site/README.md`).

Docs describe the app as it is now; development history lives in Git. New or updated
dependencies follow `docs/dependencies.md` (license inventory via
`scripts/rust-license-check.py`; release DLL allowlist in `scripts/rust-release.py`).
